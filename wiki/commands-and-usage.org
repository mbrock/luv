#+title: Commands, usage, and hidden synchronization
#+startup: overview

* Command encoding constructs a validated future action
:PROPERTIES:
:ID: C4W9RH
:END:

A WebGPU command encoder is more than a convenient builder for a native
command buffer.  Encoding and finishing establish a state-machine boundary at
which an implementation can validate structure, collect resource usages, and
prepare a self-contained future action.  Submission transfers that action to
the queue; submitted WebGPU command buffers cannot be used again.

This split allows application-side preparation to run ahead of GPU execution
without pretending the work happened synchronously.  It also gives the
implementation a durable object on which to hang the information needed by
automatic synchronization #Y8K3FD and lifetime retention #B2M7QX.

See [[https://www.w3.org/TR/webgpu/#dom-gpuqueue-submit][=GPUQueue.submit()=]] for the public submission semantics.

* Recorded commands capture dependencies
:PROPERTIES:
:ID: B2M7QX
:END:

When a draw mentions a bind group, it indirectly mentions buffers, textures,
views, and samplers.  When a copy names source and destination resources, it
also assigns usages to them.  An implementation needs to preserve these
relationships after the caller has finished constructing the command.

That captured information serves several jobs:

- keep every native dependency alive through GPU completion;
- reject a submission if a referenced public resource has become invalid in a
  way the contract forbids;
- derive the accesses and transitions required by the backend;
- identify the last submitted use relevant to mapping or destruction.

In a garbage-collected language it is tempting to believe reachability solves
this.  It only helps if the command representation itself strongly owns every
transitive dependency and if logical destruction is separately represented.
The five layers in #L8R2WF still have to be distinguished.

* Automatic synchronization means implementation-owned synchronization
:PROPERTIES:
:ID: Y8K3FD
:END:

WebGPU does not expose Vulkan pipeline barriers, access masks, stage masks, or
image-layout transitions directly.  It instead validates resource usages in
defined scopes and orders queue operations.  A Vulkan implementation must
lower that information into native synchronization and state transitions.

Therefore “the API has no barriers” does not mean barriers disappeared.  It
means the implementation owns:

1. tracking the last relevant use and state of each resource or subresource;
2. detecting transitions and conflicts between uses;
3. choosing conservative native stages, accesses, and layouts;
4. emitting the required barriers at a legal point;
5. updating tracked state only in correspondence with the submitted work.

A smaller API can choose simpler rules—for example, fewer simultaneous usage
combinations or queue-wide ordering—provided it says what the caller may rely
on and retains enough information to implement those rules.  Hiding Vulkan
syntax without assuming ownership of its correctness obligations would not be
a coherent abstraction.

* Zero initialization is part of the contract
:PROPERTIES:
:ID: Z6T4NV
:END:

WebGPU conceptually initializes resources to zero so newly allocated GPU
memory cannot reveal data from another application.  Implementations may
avoid a physical clear when they can prove the application overwrites the data
first, which turns initialization into tracked state rather than necessarily
an eager operation.

This is a particularly clear example of API simplicity relocating work.  The
caller sees deterministic initialized contents; the implementation may need
late clears, shader transformations, or initialization bookkeeping.  The
specification discusses this in [[https://www.w3.org/TR/webgpu/#security-uninitialized][Uninitialized data]].

Luv is not a browser security boundary, so it need not inherit this contract
without discussion.  But “native callers can be trusted” does not settle the
questions of deterministic behavior, debugging, portability, or whether a
future host might process untrusted workloads.

* Questions for a luv command model
:PROPERTIES:
:ID: K3P8JW
:END:

The current inspectable command structures are promising material, not a
finished answer.  Questions to carry forward include:

- At which point must every transitive resource dependency be known?
- Does finishing an encoder consume it, and is a command buffer one-shot?
- Which usage conflicts should luv reject rather than synchronize?
- Is state tracked when commands are encoded, when submitted, or both?
- What object owns retained resources between submission and completion?
- What completion primitive advances reclamation and mapping callbacks?
- Which initialization guarantees, if any, are part of luv's public contract?
- Can an API remain pleasantly synchronous while its presentation subsystem is
  asynchronous, or will those contracts eventually need to converge?

The frame-slot experiment #R3V8HC answers one narrow ownership question for
today's canvas path.  It should inform these questions without prematurely
answering all of them.
