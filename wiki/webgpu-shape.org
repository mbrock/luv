#+title: Why WebGPU has this shape
#+startup: overview

* WebGPU is a portable contract, not a thin Vulkan wrapper
:PROPERTIES:
:ID: W6P3JH
:END:

WebGPU presents a deliberately constrained vocabulary of devices, queues,
resources, pipelines, bindings, encoders, passes, and command buffers.  It can
look like a smaller collection of names borrowed from modern native APIs, but
the important simplification is semantic: an application supplies enough
information for the implementation to validate work and arrange the unsafe,
platform-specific details itself.

That contract has to survive different native APIs, driver processes, GPU
architectures, and threat models.  The WebGPU specification therefore defines
object states, allowed resource usages, command validation, initialization,
and ordering more precisely than a pleasant wrapper around Vulkan would need
to.  Its [[https://www.w3.org/TR/webgpu/#security-considerations][security considerations]] make some of this motivation explicit.

This does not make every WebGPU restriction desirable for luv.  It does make
each restriction a question worth understanding before removing it.

* The API spans several timelines
:PROPERTIES:
:ID: T4V8QM
:END:

The WebGPU specification describes a *content timeline*, a *device timeline*,
and a *queue timeline*.  Roughly, these are the caller manipulating API
objects, the implementation validating and managing the device, and the GPU
executing queued work.  They need not literally be three threads or processes;
they identify orders of events and which state is visible where.

This explains many otherwise peculiar API shapes:

- =submit= schedules work; it does not mean the GPU has finished it.
- =mapAsync= is asynchronous because host access may have to wait for older GPU
  uses of that buffer.
- =onSubmittedWorkDone= names a queue-completion point without making every
  operation synchronously drain the device.
- =destroy= changes the logical state now even when physical reclamation must
  wait for work already on the queue.

The normative vocabulary is in [[https://www.w3.org/TR/webgpu/#programming-model-timelines][WebGPU's programming-model timelines]].  For a
small native Lisp implementation the browser process model may be irrelevant,
but the separation between caller order, device bookkeeping, and GPU execution
remains real.

* Descriptors and usage flags are advance information
:PROPERTIES:
:ID: U7C2NR
:END:

WebGPU asks for resource usage flags at creation and makes pipelines and bind
groups relatively explicit.  These declarations are not merely bureaucratic
typing.  They give the implementation advance information with which it can:

- reject combinations that cannot be implemented portably;
- select compatible native memory and resource features;
- validate a command before it reaches the driver;
- compute resource-use conflicts and native state transitions;
- retain the resources on which recorded or submitted work depends.

The specification's [[https://www.w3.org/TR/webgpu/#programming-model-resource-usages][resource-usage model]] limits incompatible simultaneous
uses, which in turn limits data races and helps the same program run across
backends.  Vulkan exposes more of these choices and obligations directly.
WebGPU trades some expressiveness for a command stream whose requirements can
be discovered and checked.

This is closely connected to dependency capture #B2M7QX and automatic
synchronization #Y8K3FD.

* Simplicity is relocated, not created from nothing
:PROPERTIES:
:ID: A5K9XD
:END:

WebGPU makes application code simpler by moving substantial work into the
implementation.  A useful reading of several public operations is:

| Public shape | Work hidden behind it |
|--------------+-----------------------|
| =createBuffer({usage, size})= | native allocation choice, initialization state, usage validation |
| command encoder and passes | state-machine validation, dependency and usage collection |
| =queue.submit(...)= | native command submission, ordering, resource retention, completion tracking |
| =buffer.mapAsync(...)= | host/GPU exclusion, completion wait, cache/copy policy, callback ordering |
| =buffer.destroy()= | immediate logical invalidation and possibly deferred native destruction |
| implicit resource transitions | backend barriers, access masks, stages, and texture layouts |

“WebGPU handles it” should therefore provoke two follow-up questions: what
observable promise is being made, and which component now owns the proof that
the promise holds?  The reclamation discussion in #D3H7VK is one concrete
answer.

* What is still historical research?
:PROPERTIES:
:ID: Q8F4LC
:END:

The contract and current implementation consequences can be read from the
specification and implementations.  The design history is harder.  Useful
future archaeology includes GPUWeb issues and proposals concerning:

- why WebGPU exposes one device queue rather than Vulkan's queue-family model;
- why command buffers are one-shot;
- how the mapping state machine and usage restrictions evolved;
- which synchronization designs were considered and rejected;
- where security requirements and portability requirements independently led
  to the same restriction.

Until that work is done, these pages should say “this design permits” or “this
contract requires,” not casually attribute a single intention to the working
group.
