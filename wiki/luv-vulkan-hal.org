#+title: Field notes on the pre-split luv Vulkan HAL
#+startup: overview

* Scope and method
:PROPERTIES:
:ID: V9H2RK
:END:

These notes describe the code at commit
=7345e1551ae9ec83c23d8898ba4f500fcedc93c9=, before the ASDF-level split into
=:luv/gpu/api=, =:luv/vulkan/fundament=, =:luv/vulkan/defs=,
=:luv/vulkan=, =:luv/gpu/vulkan=, and the canvas systems.  “HAL” is convenient
shorthand here, not the name of one well-bounded component.  The object of
study was the path now housed under =gpu/api.lisp=, =gpu/vulkan.lisp=,
=vulkan/fundament.lisp=, =vulkan/defs.lisp=, =vulkan/high.lisp=, and
=canvas/vulkan.lisp=.

The categories used below are deliberately modest:

- An *observed mechanism* is something the current code demonstrably does.
- A *legible decision* is also supported by comments, structure, or history
  suggesting it was chosen intentionally.
- A *provisional constraint* may merely be what the latest vertical slice
  needed.
- A *gap* is a promise for which the code does not yet contain a complete
  proof.  It is not a demand to import a large framework.

This page is neither a specification for luv nor a list of changes already
approved.  It should make the current experiment discussable without making it
authoritative, following the wiki stance #H7QK3M.

* There are two important abstraction boundaries
:PROPERTIES:
:ID: C5M8QD
:END:

The stack currently looks roughly like this:

#+begin_example
application and McCLIM compositor
       |
       v
gpu/api.lisp                  portable-looking GPU vocabulary
       |
       v
gpu/vulkan.lisp           Vulkan interpretation and GPU object wrappers
       |                         ^
       v                         | canvas/vulkan.lisp also enters here
vulkan/defs.lisp + high.lisp    owned, incomplete Vulkan vocabulary
       |
       v
invocation.lisp           reified call / invoker protocol
       |
       v
CFFI and the Vulkan loader
#+end_example

The lower boundary was unusually explicit even before the file split.
=vulkan/defs.lisp= declares only the Vulkan structures, enumerants, and calls
needed by concrete backend work, while =vulkan/fundament.lisp= contains the
binding machinery.  Each foreign call is also a class of invocation routed
through an invoker, so tracing or replacing the boundary is ordinary method
dispatch.  This is a clear architectural decision, visible in
[[file:../invocation.lisp::(defclass invocation][the general invocation protocol]] and
[[file:../vulkan/fundament.lisp::(defmacro defvkfun][=defvkfun=]].

The upper boundary is younger.  =gpu/api.lisp= supplies backend-neutral-looking
classes and generic functions, while =gpu/vulkan.lisp= immediately lowers them
to Vulkan.  It is useful to distinguish “the owned Vulkan binding is a small
coherent boundary” from the stronger and currently unproven claim “luv has a
coherent portable GPU HAL.”

* The portable API is a seam, but not yet an isolated component
:PROPERTIES:
:ID: A7N4XP
:END:

There is a real source seam: =gpu/api.lisp= contains no Vulkan calls and says that
presentation is outside its API.  Commands are dispatched through generic
functions, so another backend could specialize the same vocabulary.

In the pre-split tree there was not yet a separately loadable abstract
interface: =:luv/gpu= loaded the generic API, Vulkan binding, and Vulkan
backend together.  The new =:luv/gpu/api= system now gives that API an ASDF
boundary, while =:luv/gpu= remains the convenient Vulkan-backed bundle.
The =LUV= package still exports the generic GPU vocabulary alongside
=vulkan-gpu-provider= and Vulkan-specific conditions.

At this page's snapshot, Metal was a direction rather than a tested contract.
That observation is now historical: #5A7QDE supplies a second provider and
canvas-context implementation which presents through the shared command
vocabulary.  It has already confirmed the source seam and exposed the next
untested boundary.  =shader-module-descriptor= still merely says =code= while
the Vulkan implementation requires SPIR-V words; #OV1AZO and #58IDSR now use
the concrete Metal target to decide whether artifact kind belongs in that
descriptor or behind a compiler-owned boundary.

This arrangement is excellent for rapid vertical slices.  Its present cost is
that a Vulkan implementation convenience can become part of the apparent HAL
before a second backend has tested the boundary.

* Device selection is mostly implicit policy
:PROPERTIES:
:ID: J6T2VA
:END:

One call to =request-gpu-device= currently creates and owns a Vulkan instance,
chooses the first enumerated physical device, chooses the first queue family
supporting both graphics and compute, creates one logical device, and exposes
one default queue.  There is no separate adapter object or capability enquiry.
Non-empty required feature or limit sets are rejected rather than negotiated.

Presentation capability is partly determined by ambient SDL state when the
device is requested.  If SDL video is initialized, around methods add SDL's
instance extensions and =VK_KHR_swapchain=.  A later canvas context checks
that the chosen queue family can present to its newly created surface.  Thus
an offscreen device requested too early cannot simply acquire presentation
capability later, and a device selected without a surface may turn out not to
present to it.

Some of this may be an intentionally tiny one-device policy.  What is not yet
decided is how a caller states preferences, discovers limits, distinguishes an
adapter from a device, or requests a device suitable for a future surface
without relying on initialization order.

Relevant code begins at
[[file:../gpu/vulkan.lisp::(defmethod request-gpu-device][=request-gpu-device=]] and
[[file:../canvas/vulkan.lisp::(defmethod vulkan-provider-instance-options :around][the SDL extension augmentation]].

* Several local ownership rules are admirably concrete
:PROPERTIES:
:ID: O3K6TW
:END:

The backend frequently chooses simple one-owner relationships rather than
general allocators:

- A texture owns its image memory; a borrowed swapchain texture says
  =owned-p nil= explicitly.
- A texture view strongly references its texture.
- A bind group owns one descriptor pool and references its layout, view,
  sampler, and optional uniform buffer.
- A pipeline owns its native pipeline layout and references its bind-group
  layout.
- Each command encoder creates one transient command pool and one primary
  command buffer.
- =finish= transfers that command pool, command buffer, texture-layout facts,
  and temporary native resources into one =vulkan-gpu-command-buffer=.
- Framebuffers and texture-upload staging allocations are tagged native
  resources owned first by the encoder and then by the finished command
  buffer.
- Render passes are cached per device and format and retired with the device.

Creation paths use =unwind-protect= consistently to clean up partially created
native objects.  Destruction is explicit and mostly idempotent at the wrapper
level.  These are good small-system properties: one can usually point at the
object responsible for a native handle.

The transfer in
[[file:../gpu/vulkan.lisp::(defmethod finish][=finish=]] is especially worth retaining
as the lifetime model grows.  It is already the seed of a submission bundle,
even though it does not yet contain every dependency.

* Inspectable commands are inputs, not a retained command IR
:PROPERTIES:
:ID: D8F3QM
:END:

The command structs in =gpu/api.lisp= and double dispatch through =encode= are a
legible decision.  Command kinds are separated by scope: queue commands,
command-encoder commands, render-pass commands, and compute-pass commands.
Pass encoders enforce an explicit recording/ended state and one active pass per
command encoder.  Finished command buffers are one-shot: submission changes
their state from =ready= to =submitted=.

The current backend lowers each inspectable command immediately into its
Vulkan command buffer.  The finished =gpu-command-buffer= does not retain the
high-level command occurrences and cannot be inspected, transformed, replayed,
or lowered by another backend.  “Inspectable commands” currently means that
the protocol input is data at the moment of encoding, not that GPU work remains
an inspectable intermediate representation.

The vocabulary can also get ahead of the implemented protocol.  For example,
=gpu-set-viewport-command= exists, but has no constructor exported and no
backend =encode= method; render-pass creation instead records a fixed viewport
and scissor directly.  This is harmless experimental residue, but it shows
that there is no current completeness rule connecting public command types,
constructors, and backend support.

This leaves an open choice: should command data primarily enable pleasant
double dispatch and tracing, or should it become a durable backend-independent
IR?  Either can be coherent, but they imply different ownership and validation
boundaries.

* Public submission is the current lifetime proof
:PROPERTIES:
:ID: S8R5JV
:END:

Ordinary =submit= sends a batch to Vulkan, marks each command buffer submitted,
updates scheduled texture layouts, and then calls =vkQueueWaitIdle=.  Returning
from =submit= therefore proves that command pools, descriptor sets, pipelines,
buffers, textures, and temporary native resources used by the batch are no
longer in flight.  This is simple and safe for callers that destroy resources
after submission returns, but it prevents overlap.

Canvas presentation uses the internal =submit-vulkan-command-buffers= entry
with a fence and no queue-idle wait.  A frame slot retains the command buffer
until that fence signals.  This is the narrow asynchronous exception described
by #F7Q2KM.

There is no general submission-lifetime owner.  A finished command buffer
retains textures it transitions and its tagged native resources, but not the
pipelines, bind groups, descriptor resources, texture views, samplers, or
uniform buffers referenced by recorded commands.  The pass encoder temporarily
held a pipeline and bind group while recording, but those references are not
transferred by =finish=.

Current presentation happens to keep its pipelines and per-image bind groups
alive elsewhere.  That makes the present compositor work; it does not make the
asynchronous submission primitive generally safe against explicit destruction.
If the last application reference merely disappears, the absence of finalizers
turns the missing ownership edge into a leak rather than an early native free.
A future asynchronous public submit needs complete transitive dependency
capture and a retirement rule, not merely a fence parameter.  See the five
lifetimes #L8R2WF and wgpu example #G5X8BN.

* Texture layout tracking is scheduled state with a narrow hazard model
:PROPERTIES:
:ID: X2D7MF
:END:

Each Vulkan texture wrapper has one current layout.  An encoder records the
initial layout it observed and a sequence of final layouts.  At submission,
the backend checks that every command buffer's initial assumptions match the
scheduled state produced by earlier buffers in the same batch, then updates
each texture wrapper to the final scheduled layout immediately after queueing
the work.

This is a meaningful distinction: the layout slot represents the state ordered
on the queue, not necessarily work already completed.  On a single ordered
queue that can correctly prepare the next submission without waiting.

The present tracker is deliberately small:

- one state covers the whole image, which matches today's single-mip,
  single-layer textures;
- barriers are selected from a fixed mapping of layouts to access and stage
  masks;
- a barrier is emitted only when the layout changes;
- separately encoded command buffers are rejected if an earlier submission
  changed the layout they assumed.

Layout alone is not a complete access-hazard model.  Two dispatches can both
use a storage image in =general= while still requiring a memory dependency
between a write and a later read or write.  Because the layout does not change,
the current code emits no barrier.  Likewise, there is no submit-time rebasing
of independently encoded command buffers and no locking around the global
layout slots.

The code therefore supports the access patterns exercised by current demos,
not yet the general “automatic synchronization” contract discussed in
#Y8K3FD.

* Buffer mapping is a special uniform path, not yet a memory model
:PROPERTIES:
:ID: B9Q4LC
:END:

The only public buffer slice accepts usage exactly equal to =(:uniform)=.  It
chooses host-visible, host-coherent memory, maps it for the buffer's whole
lifetime, and lets =write-buffer= copy a one-dimensional =single-float= array
directly into the mapping.

This is a pragmatic path for the compositor's tiny uniforms.  Host coherence
removes an explicit cache flush requirement; it does not prevent the host from
overwriting bytes while the GPU reads them.  The current compositor supplies
the missing exclusion rule outside the HAL by using one uniform buffer per
swapchain image and writing only after that image is reacquired.

The buffer API itself does not record that rule.  It has no mapped/unmapped
state, pending map operation, range ownership, submission-use tracking,
staging path, readback path, or synchronization around =write-buffer=.  Calling
=write-buffer= at an arbitrary time is therefore only safe by convention.

There is also no WebGPU-like zero-initialization tracker.  New buffer memory
and textures begin with whatever semantics the concrete Vulkan path gives
them, and current callers are expected to clear or overwrite before reading.
Whether luv wants deterministic initialization is an open contract question,
not something inherited merely because the names resemble WebGPU; see
#Z6T4NV.

* Presentation is separate, but relies on backend internals
:PROPERTIES:
:ID: P5V8KN
:END:

Keeping canvas and swapchain concepts out of =gpu/api.lisp= is a clear and useful
decision.  =:luv/gpu= can run offscreen, while =:luv/canvas= adds SDL surface
and presentation policy.  A context borrows its configured device rather than
owning it, and swapchain images are explicitly represented as borrowed GPU
textures.

The current policy is intentionally fixed: =:copy-dst= swapchain usage, FIFO
present mode, one more than the minimum image count, and at most two frame
slots.  Unconfiguration waits for the whole device to become idle before
destroying the swapchain-owned structures.

The separation is not yet a narrow public interface.  =canvas/vulkan.lisp=
calls backend-internal texture transition and submission functions and reaches
Vulkan-specific slots.  This direct composition is readable, but a second
backend will have to reveal which part is the generic canvas contract and
which part is Vulkan presentation machinery.

Swapchain change handling is also incomplete.  =suboptimal= acquisition is
accepted and ignored; an out-of-date result becomes a Vulkan call error rather
than a context reconfiguration path.  Resize propagation may proactively
reconfigure normal cases, but recovery is not expressed as a presentation
state machine.

* Explicit destruction does not yet compose into device ownership
:PROPERTIES:
:ID: G6C2TX
:END:

There are no finalizers.  Losing the last Lisp reference does not destroy a GPU
object, so the current API is manual despite running in a garbage-collected
language.  Explicit =destroy= usually calls the corresponding Vulkan destroy
operation immediately and marks the wrapper destroyed.  It does not defer
destruction through a completion frontier #P6Q4MT.

The device does not keep a registry of child buffers, textures, views,
samplers, pipelines, layouts, bind groups, or command buffers.  Device
destruction waits for idle and destroys its cached render passes, then calls
=vkDestroyDevice=.  Vulkan's
[[https://docs.vulkan.org/refpages/latest/refpages/source/vkDestroyDevice.html][=vkDestroyDevice= valid-usage rule]] requires all destroyable child objects to
have been destroyed or freed first.  Current demos manually destroy their
resources in the expected order, but =destroy device= does not itself establish
that precondition.

After the device wrapper is marked destroyed, later child =destroy= methods
skip their native destroy calls and merely mark the child wrapper.  This avoids
calling through a dead device but cannot repair children omitted before
=vkDestroyDevice=.

Relations between children are only partly guarded.  A view retains its
texture and a bind group retains its descriptor resources, but a caller can
still explicitly destroy one of those resources and later use the still-live
parent wrapper.  Texture use is often rechecked during encoding; view and
sampler liveness are not comprehensively revalidated.  The public meaning of
=destroy= is consequently immediate native teardown constrained by caller
discipline, not the logical/physical split #D3H7VK.

* The error vocabulary is useful but not yet one contract
:PROPERTIES:
:ID: E3W7RH
:END:

The GPU layer has typed conditions for invalid object state, destroyed
objects, device mismatch, usage mismatch, and failed requests.  This is useful
REPL-facing structure.  The Vulkan binding also translates failed =VkResult=
values into =vulkan-call-error= while retaining the operation name.

The boundary between validation errors and backend failures is still porous.
Vulkan-specific errors are exported beside nominally portable GPU errors.
=reject-gpu-request= always labels its condition operation as =:create= even
when it is used while encoding commands or setting pass state.  Some malformed
property-list descriptors can reach ordinary Lisp type errors before a GPU
condition.  Device loss, out-of-memory classification, asynchronous errors,
validation scopes, and recoverable swapchain results have no common model.

This is less a bug than evidence that the condition hierarchy grew alongside
vertical slices.  A later contract should decide which failures are portable
API facts, which are backend diagnostics, and which invalidate a device or
submission.

* Decisions that look worth preserving
:PROPERTIES:
:ID: R8M4WC
:END:

Even where the general contract is missing, several tendencies look
generative:

- grow the Vulkan binding only from concrete backend needs;
- keep the actual Vulkan treaty visible rather than generating an enormous
  opaque binding;
- reify driver crossings at one general invocation boundary;
- use command scope types and double dispatch instead of a giant opcode
  switch;
- make borrowed native ownership explicit;
- transfer command-pool and temporary-resource ownership at =finish=;
- use transactional creation cleanup and idempotent explicit teardown;
- keep platform window policy out of the offscreen GPU vocabulary.

These principles do not determine whether the final HAL resembles WebGPU.
They describe the style in which missing semantics can be made concrete.

* Questions now made visible
:PROPERTIES:
:ID: Z4K7NP
:END:

The most consequential questions are not “which Vulkan function is missing?”
but ownership and contract questions:

1. Is synchronous public submission an intentional small-API guarantee or
   only a bootstrap until completion tracking exists?
2. What complete set of resources does a finished command buffer own, and
   what object owns that set after submission?
3. Does =destroy= mean immediate native teardown, logical invalidation plus
   deferred teardown, or different things for different resource classes?
4. Will the HAL track access hazards and scheduled state, or expose enough
   synchronization that callers own part of the proof?
5. What excludes host writes from GPU reads of persistently mapped buffers?
6. What is the portable shader representation?
7. How are adapters, capabilities, presentation suitability, and device loss
   represented without importing all of WebGPU?
8. Is the inspectable command vocabulary a transient dispatch protocol or a
   durable IR?
9. Does the device own and retire all children, or must callers obey an
   explicit destruction order that can be checked?
10. Which deterministic initialization guarantees belong to luv?

A useful next design step would choose one concrete lifecycle—probably
encode → finish → submit → completion → destroy—and make every ownership edge
and state transition explicit for buffers, bind groups, pipelines, command
resources, and a canvas image.  That would test several questions together
without requiring a broad rewrite.
