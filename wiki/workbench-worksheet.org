#+startup: overview

* Intent and non-goals
:PROPERTIES:
:ID: Z96DF9
:END:

This is the living worksheet for the screen-space application substrate
described by #M9MI6Y.  The architecture record says why the substrate exists
and which decisions constrain it; this page sequences experiments, records
what they teach, and names exactly one next action.  Execution threads are
replaceable working sessions.  They read and update this worksheet rather than
becoming the only place where an architectural decision survives.

The intended result is one Luv-owned workbench over any conforming graphical
application: compact status, lobby, metabar, M-x, source review, and later
presentation-typed prompts share one technical visual language and one model
of panes, focus, modality, input, rendering, and release.  Their value comes
from being available without an atelier inventing a host adapter for every
tool.  Luft is the first conforming atelier.

This work does /not/ define a common game engine, absorb Luft's site inspector
or authored tools into global chrome, generalize Luvcraft's spatial overlays,
or preserve arbitrary third-party extension registration.  Luvcraft migration
is deferred until Luft proves the substrate.  Its scene, world-panel,
viewmodel, and world-focus machinery may remain independent even when a later
fixed-screen workbench supersedes it temporarily.

* Established invariants
:PROPERTIES:
:ID: H51JQ0
:END:

- Workbench state and GPU-resource mutation cross the native frame boundary.
- Asynchronous work quiesces before a terminal canvas fence.  A source fetch
  may be cancelled; a checkout mutation and live ASDF assimilation complete
  before release.
- Native input reaches the shell before application input.  Passive,
  modeless, transient, and modal panes have explicit behavior rather than
  numeric event priority.
- Opening interactive shell UI clears held application input before swallowing
  corresponding release events and suspends relative pointer capture through
  an explicit application token.
- McCLIM authors retained semantic commands.  The shell does not rasterize a
  pane texture, acquire a drawable, submit a queue, or own an application
  renderer.
- Shell resources and workers are released while the context and GPU device
  remain live; application renderer resources, canvas, and device retain their
  existing terminal order.
- Application stop closes shell admission atomically.  Startup or publication
  which loses that race consumes and releases its own resources.
- The application supplies semantic values and commands, not per-pane
  compositors, placement matrices, inverse pointer transforms, or open/close
  adapters.

* Current architecture
:PROPERTIES:
:ID: 8VVBDJ
:END:

The current implementation is the evidence and migration source, not the
desired boundary.

- [[file:../hal/canvas.lisp][hal/canvas.lisp]] owns the portable presentation transaction.
  =PRESENT-CANVAS-FRAME= acquires a surface and encoder, invokes the
  application, then completes presentation.  A shell postlude here could
  composite after an application without entering its renderer.
- [[file:../hal/sdl/canvas.lisp][hal/sdl/canvas.lisp]] owns the native SDL event and frame loop.  It is the
  natural outer boundary for shell-first input and frame-boundary requests.
- [[file:../mcclim/direct-compositor.lisp][mcclim/direct-compositor.lisp]] already replays retained McCLIM commands into
  a caller-owned render pass.
- [[file:../mcclim/gpu.lisp][mcclim/gpu.lisp]] already combines descendant sheet streams in painter order.
  The first proof must establish that overlapping child panes preserve clips,
  transforms, and native-density text in one embedded frame.
- [[file:../mcclim/mirror.lisp][mcclim/mirror.lisp]] translates native events through sheets, but embedded
  top-level mirrors do not yet expose ordinary viewport resize and direct
  canvas-event dispatch as a clean public protocol.
- [[file:../luft/render/instruments.lisp][luft/render/instruments.lisp]] is a small window manager and lifecycle registry:
  numeric visual/input order, refresh, encoding, event interception,
  quiescence, and release.  Status, lobby, metabar, M-x, and source review use
  it visually; Tracy and the application agent use it invisibly.
- [[file:../luft/render/studio.lisp][luft/render/studio.lisp]] owns the first conforming application, its renderer,
  ordinary atelier commands, site inspector, input state, and terminal release
  order.  Those application concerns remain Luft's.

The applications-by-tools adapter matrix and the focused-pointer routing bug
in the current Luvcraft M-x/source panels are deletion pressure, not contracts
to reproduce.

* Open technical questions
:PROPERTIES:
:ID: PMDM1O
:END:

1. Can one transparent full-viewport embedded McCLIM frame retain and replay
   overlapping child panes with correct logical resize, clipping, painter
   order, and native-density rendering?
2. What is the smallest public operation for resizing an embedded top-level
   mirror and laying out its children after an SDL logical-size change?
3. Can canvas events enter that mirror's normal sheet dispatch without making
   it the canvas's sole native handler?
4. Should the portable presentation transaction own exactly one
   =APPLICATION-SHELL= postlude, or does backend behavior require the
   application to call the shell inside its final pass?  Prefer the postlude;
   decide from the backend proof rather than aesthetics.
5. Is shell chrome included in application screenshots and films, excluded
   like browser devtools, or selectable?  Do not let this choice complicate
   the first on-screen proof.
6. Which application-input suspension token is sufficient for Luft without
   importing Luvcraft camera/world-focus semantics?
7. How will incremental presentation-typed prompting replace blocking CLIM
   =ACCEPT= on the canvas thread?  This is downstream of basic modal routing.

* Decision log
:PROPERTIES:
:ID: 3LH9F7
:END:

** 2026-08-28 — The workbench is substrate, not an extension registry

Status, lobby, metabar, M-x, and source review are known screen-space
affordances supplied by Luv.  Their usefulness comes from not requiring an
atelier to author a host integration for each one.  Do not hoist Luft's
instrument protocol or invent another arbitrary registration API.

** 2026-08-28 — Screen-space shell and application atelier remain distinct

The shell owns global panes, focus, modality, technical visual language, and
service views.  Luft owns its renderer, world, site inspector, authored tools,
commands, semantic field values, and resource release order.

** 2026-08-28 — Luft proves the protocol before Luvcraft migrates

Luft is small enough to expose the right application boundary.  Luvcraft's
spatial overlays and world focus are neither the design template nor immediate
cleanup scope.

** 2026-08-28 — Prefer one workbench frame and one presentation postlude

One layered frame lets McCLIM sheet geometry own rendering placement and input
hit testing.  One shell postlude in the portable presentation transaction is
more substrate-like than an application renderer callback.  Both remain
hypotheses until #BY51K0 proves backend behavior.
